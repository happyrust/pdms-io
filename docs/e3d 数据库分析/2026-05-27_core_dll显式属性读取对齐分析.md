# core.dll 显式属性读取对齐分析

> 日期：2026-05-27  
> 目标：用 IDA 中的 `core.dll` 读取模型校准 `parse_pdms_db` 的显式属性解析逻辑，避免继续沿用“负 hash 即表达式”的线性扫描策略。

## 1. 背景

`/Volumes/DPC/parser-error/parse-1.log` 中出现两类相关报错：

```text
解析=15213/81343 表达式属性退出: "PHEI", [...]
解析=15213/127718 表达式属性退出: "", [...]
```

前者来自 `PHEI` 显式表达式属性解析失败，后者来自后续 `0xFFFFFFFF` 被误当作负数表达式 hash 继续解析，最终得到空属性名。

当前 Rust 侧 `parse_raw_explicit_attrs` 的关键问题是：在读取显式条目 header 之前，就用 `check_is_expr(hash_val)` 判断是否进入表达式解析。`check_is_expr` 目前对任意负数返回 true，这会让显式条目绕过 core.dll 的通用边界规则。

## 2. IDA 环境

本轮分析的 IDB：

```text
path: /Volumes/DPC/reverse/core.dll
module: core.dll
base: 0x10000000
```

这是 2.x 地址体系，本文地址均基于该 IDB。

## 3. core.dll 的真实读取链路

core.dll 不是把元素记录后缀当作“属性 token 流”一次性贪婪扫描，而是按属性定义读取指定属性：

```text
GATINT / GATREA / GATTXT
  -> DB_Attribute::findAttribute(hash)
  -> DB_Element(refno)
  -> DB_Qualifier
  -> DB_Element::getAtt(attribute, qualifier, out)
  -> DB_Element::internalGetAtt(...)
  -> DB_Element::dabGetAtt(attr_id, out)
  -> db4_get_ce_att(...)
```

关键函数：

| 地址 | 函数 | 结论 |
| --- | --- | --- |
| `0x104b79f0` | `DB_Element::getAtt(int)` | 调 `internalGetAtt`，成功后处理 UDA old/new 格式 |
| `0x104b4ac0` | `DB_Element::internalGetAtt(int)` | 校验 `dtyp/size/protected/UDA/pseudo`，然后按需走 DAB |
| `0x104a0790` | `DB_Element::dabGetAtt(int)` | 先 `elGotoCPP(this, 1)`，再调用 int 标量取值器 |
| `0x104a09e0` | `DB_Element::dabGetAtt(real)` | 先 `elGotoCPP(this, 1)`，再调用 real 标量取值器 |
| `0x104abf30` | `DB_Element::dabGetAtt(string)` | 先查属性长度，再按 string 取值器读取 |
| `0x10612a50` | `db4_get_ce_att` | 当前元素属性读取核心，处理隐式 offset 和显式表扫描 |

DAB 操作码包装：

| 包装函数 | 操作码 | 用途 |
| --- | ---: | --- |
| `sub_105DEA00` | `490` | int 标量 |
| `sub_105DEB80` | `492` | int array |
| `sub_105DF1F0` | `500` | table/string |
| `sub_105DF370` | `502` | real 标量 |
| `sub_105DF4F0` | `504` | real array |
| `sub_105DF670` | `506` | string |
| `db_get_attribute_info` / `sub_105EF680` | `62` | 属性信息查询 |

## 4. 显式属性条目格式

`db4_get_ce_att` 在显式表中查找属性时，核心扫描逻辑等价于：

```c
idx = 4;
while (explicit_words[idx] != requested_attr_hash) {
    idx += (explicit_words[idx + 1] & 0x03ffffff) + 2;
}

packed = explicit_words[idx + 1];
dab_type = packed >> 26;
payload_len_words = packed & 0x03ffffff;
payload = &explicit_words[idx + 2];
```

因此显式条目不是当前 Rust 代码假设的“表达式属性独立结构”，而是统一结构：

```text
word[0]  attr_hash
word[1]  packed_header = (dab_type << 26) | payload_len_words
word[2..2+payload_len_words] payload
```

扫描下一个条目的步长必须是：

```text
2 + payload_len_words
```

其中 `2` 表示 `attr_hash + packed_header`。

## 5. PHEI 样本重新解读

`parse-1.log` 中 PHEI 片段开头为：

```text
FFF520EF 1C00001A 00000019 00000019 ...
```

按 core.dll 规则解释：

```text
attr_hash          = 0xFFF520EF   // PHEI
packed_header      = 0x1C00001A
dab_type           = 0x1C00001A >> 26 = 7
payload_len_words  = 0x1C00001A & 0x03FFFFFF = 26
payload[0]         = 0x00000019 = 25
```

结论：

- `0x1C00001A` 不是表达式专用 envelope，而是显式条目 packed header。
- `dab_type=7` 对应 core.dll 的 int-array 类读取路径。
- `payload_len_words=26` 表示 payload 总长为 26 words。
- `payload[0]=25` 表示数组 count 为 25，后续 25 个 words 才是表达式 opcode 数据。
- 整个 PHEI 条目应为 `2 + 26 = 28 words = 112 bytes`。
- 当前日志里只剩 `2 + 21` 个 words，少了 5 个 payload words，说明上层显式块/追加段拼接或边界切片已经丢尾。

所以当前错误的第一根因不是 opcode decoder 不认识某个 opcode，而是条目边界没有按 core.dll 的 packed header 和 segment 规则保证完整。

## 6. Rust 侧现状问题

当前位置：

```text
crates/parse_pdms_db/src/parse.rs
parse_raw_explicit_attrs(...)
```

现有逻辑：

```rust
let hash_val = convert_to_hash(&residual[..4]);
if check_is_expr(hash_val) {
    parse_expression_attr_nom(residual, refno.0)
}
```

问题：

1. 表达式分支在解析 packed header 之前发生，绕过了 `payload_len_words` 边界。
2. `check_is_expr(hash_val)` 对任意负数返回 true，导致 `0xFFFFFFFF` 这类 padding/sentinel/tail word 被误判。
3. `parse_expression_attr_nom` 接收到的是从 `hash` 开始的整段 residual，而不是已经按 explicit entry 切好的 payload。
4. PHEI 缺尾时，错误被报告成“表达式解析失败”，而不是更准确的“显式条目 payload 不完整”。

## 7. 建议的 core-aligned Rust 结构

建议把显式属性解析拆成三层。

### 7.1 ElementRecordReader

职责：

- 按 RefNo 定位完整元素记录。
- 解析 implicit area、members block、explicit block。
- 负责 `0x00000007` 追加段拼接。
- 对外保证 explicit payload 是完整的连续 words。

这层如果发现 PHEI 所在 explicit block 声明长度不够，应报告块/段级错误，不能交给表达式 decoder 猜。

### 7.2 ExplicitEntryTable

职责：

- 按 core.dll 的 packed header 规则把显式 payload 切成 entries。
- 不做类型语义解析，只负责边界。

建议数据结构：

```rust
struct ExplicitEntry<'a> {
    hash: i32,
    dab_type: u8,
    payload_len_words: usize,
    payload_words: &'a [i32],
}
```

解析不变量：

```text
entry_total_words = 2 + payload_len_words
next_idx = idx + entry_total_words
```

遇到以下情况应停止或报错，而不是继续当作属性：

- `hash == 0`
- `hash == -1`
- `packed_header == 0`
- `payload_len_words` 越界
- 下一个 word 落在 padding/segment marker 区

### 7.3 CoreLikeGetAtt

职责：

- 输入 `attr_hash + AttrInfo + ElementContext`。
- 先按 metadata 判断是否有 implicit offset。
- 如果没有 implicit offset，再到 `ExplicitEntryTable` 查 hash。
- 找到 entry 后，按 `dab_type` 和 `AttrInfo` 解码。

这比当前“边扫边反序列化所有属性”的方式更接近 core.dll。

### 7.4 ExpressionDecoder

职责：

- 只处理已经切好的 entry payload。
- 对 `dab_type=7` 的表达式属性：

```text
count = payload_words[0]
opcodes = payload_words[1..1+count]
```

如果 `payload_len_words < 1 + count`，返回：

```text
IncompleteExplicitEntry {
    hash,
    declared_payload_words,
    count,
    available_words,
}
```

不要进入 opcode fallback，也不要把后续 `0xFFFFFFFF` 作为下一属性。

## 8. 对当前 bug 的直接修复方向

短期修复可以分两步：

1. 在 `parse_raw_explicit_attrs` 前面先解析统一 explicit entry header：

```rust
let hash = read_i32(words[idx]);
let packed = read_u32(words[idx + 1]);
let dab_type = (packed >> 26) as u8;
let payload_len_words = (packed & 0x03ff_ffff) as usize;
```

2. 表达式判定必须移动到 entry 边界之后：

```rust
if is_expression_attr(hash, attr_name, attr_info) {
    decode_expression_from_entry_payload(dab_type, payload_words)
}
```

`check_is_expr(hash < 0)` 应废弃或收窄为：

```text
hash != -1
hash != 0
hash 命中 EXPR_ATT_SET 或 AttrInfo 标记为表达式/规则类
```

## 10. 结论

要和 core.dll 保持一致，Rust 侧不应以“负 hash 表达式”作为显式属性解析入口。正确入口应是：

```text
完整元素记录
  -> 完整 explicit block/segment payload
  -> packed explicit entry table
  -> 按 attr_hash + metadata 查询指定 entry
  -> 按 dab_type 解码
  -> 表达式属性再进入 expression decoder
```

PHEI 当前失败的关键证据是：`0x1C00001A` 声明了 `dab_type=7`、`payload_len_words=26`，但日志中只有 21 个 payload words。先修 entry/block 完整性，再修表达式 opcode，顺序不能反。
